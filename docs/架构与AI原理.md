# 朵朵的 24 点：架构与 AI 原理

这份文档解释三件事：**原版是怎么做的**、**24 点的求解 AI 到底是怎么算的**、
以及**我们在复刻时做了哪些取舍、踩了哪些坑**。

---

## 一、原版到底是什么（扒开看的）

### 1.1 先把原版跑起来

4399 的页面脚本把游戏放在一个 iframe 里，地址藏在 `_strGamePath` 变量中，不带域名。
用真实浏览器（Playwright）打开播放页、监听网络请求，就能拿到真正的地址：

```
https://szhong.4399.com/4399swf/upload_swf/ftp23/csya/20171121/3/index.html
```

带上 `Referer: https://www.4399.com/flash/193616_2.htm` 才允许直接访问，否则会跳"访问错误"。
进去以后可以确认：

| 项目 | 实际情况 |
|---|---|
| 引擎 | **Cocos Creator** 导出（`cocos2d-js-min.js` + `main.js` + `src/project.js`） |
| 项目名 | `Math24` |
| 设计画布 | 竖屏 `338×600`（4399 页面里的 `_w=338, _h=600`） |
| 场景 | `MainScene`（主菜单）、`LevelScene`+`StageView`（选关）、`GameScene`（闯关）、`TutorialScene`（第 1 关教学）、`LevelUpScene`（结算）、`TimeMode*`（竞速模式） |
| 素材 | `title.png`（logo）、`bg.png`（近纯白）、`levelSprites.png`（关卡按钮 4 态）、`AutoAtlas-*.png`（UI 图集）、一个 `btn.mp3` |

### 1.2 最关键的发现：原版**没有求解器**

`GameScene` 里答案是这样来的：

```js
this.answer.string = c.LEVEL_DATA[c.level-1][4];
```

`LEVEL_DATA` 是一个 300 项的硬编码数组，每项长这样：

```js
["5","3","7","4","(5+3)×(7-4)"],
["3","8","1","1","3×8×1×1"],
["6","4","2","3","6×4×(3-2)"],
```

也就是说，**300 关的题目和解法全是人工写好的字符串**，没有搜索、没有推理。
这带来两个后果：

1. 提示和答案只能"照本宣科"，无法针对玩家**当前盘面**给建议（玩家自己走了一半就帮不上了）。
2. 出题量被锁死，想加第 301 关必须手工写答案。原版的"自由练习"其实是竞速模式里
   `randomQuestion()` 从同一份 `LEVEL_DATA` 里随机取题。

还有一个隐患在 `Card.getNumber()`：

```js
getNumber: function () {
  this.number > 23.9 && this.number < 24.1 && (this.number = 24);
  return this.number;
}
```

它用浮点数做四则运算，再用 **±0.1 的容差**去判断是否等于 24。而且分数表示
（`numerator/denominator`）**全程不约分**，分母会迅速膨胀。对 `3 3 8 8` 这种题，
浮点路径算出来是 `23.999999999999996`——正好压在容差里才判对。

> 本项目在这两点上都做了相反的取舍：写出**真正的求解器**，全程用**既约分数**、零容差判等。
> 这样提示能针对当前盘面、答案永远唯一可信、题目可以是无限道。

### 1.3 原版的真实界面（复刻依据）

把游戏本体跑起来逐屏截图之后，实际视觉是：

| 位置 | 原版做法 |
|---|---|
| 背景 | **纯白**（`bg.png` 几乎是纯白，只有极淡的纸面斑点） |
| Logo | 多彩字 "Make to" + **橙色爆炸贴「24」**（早期宣传图上的绿色是旧版本） |
| 主菜单 | 两个圆角矩形大按钮：绿色「闯关」、橙色「竞速」，都有**底部深色边** |
| 牌桌 | 4 张牌排成 **2×2 宫格**，薄荷绿圆角横块 + 白色粗数字 + 底部深边 |
| 运算符 | **橙色纯字形**，没有底色；选中后才加绿色圆角底 |
| 顶栏 | 左「←」、中间「幼儿园1级」、右侧「↻ 重来」和「💡 提示」 |
| 选关 | 4 列 × 5 行宫格，当前关绿色、已过关薄荷绿、未解锁灰色 + **白色挂锁**，第 20 关显示「考试」 |
| 15 个等级 | 其实是**段位称号**：幼儿园 → 小学生 → … → 数学之王 |
| 提示机制 | 每关 3 次，用完按钮变灰 |

本项目按这份清单把界面整套重做了一遍（这就是第一版被评价为"太丑"之后返工的原因）。

### 1.4 那"AI"到底在哪

原版没有 AI。24 点这个游戏的"智能"部分，其实是**可穷举的确定性搜索**——
见下一节。真正需要设计的是**难度曲线**和**交互**，而不是算法本身。

## 二、AI：24 点求解器

### 2.1 问题的数学结构

用 4 个数做 3 次二元运算，运算顺序对应一棵 **4 个叶子的二叉树**。
4 个叶子的二叉树形态恰好是卡特兰数 `C₃ = 5`：

```
((a∘b)∘c)∘d      (a∘(b∘c))∘d      (a∘b)∘(c∘d)      a∘((b∘c)∘d)      a∘(b∘(c∘d))
```

于是候选表达式的总数是：

```
5 种括号结构 × 4! 种数字排列 × 4³ 种运算符组合 = 7680
```

**7680 是一个很小的数字**，所以 24 点不需要任何"智能"算法——
它是**可完全穷举的**。游戏里所谓的 "AI"，本质就是一个穷举搜索器。

### 2.2 两条实现路线

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 模板穷举** | 硬编码上面 5 种括号模板，套 24 个排列 × 64 组运算符 | 直白、好理解 | 代码冗长，模板写错不容易发现 |
| **B. 递归归约** | 每次任取两张牌合并成一张新牌，递归到只剩一张 | 代码短，**天然覆盖全部 5 种括号结构** | 结果里含交换律重复，需要去重 |

本项目**主体用 B**（`solveAll`），但在测试里**用 A 独立实现了一份**当作对照 ——
两套结构完全不同的实现在 1~13 全部 1820 个组合上必须给出完全一致的结论。
这比"自己验自己"可靠得多。

### 2.3 为什么必须用分数（这一步最容易做错）

经典题目 `3 3 8 8`，唯一解是 `8 ÷ (3 − 8 ÷ 3) = 24`。用浮点数算：

```js
8/3                  // 2.6666666666666665
3 - 8/3              // 0.3333333333333335
8 / (3 - 8/3)        // 23.999999999999996   ← 不等于 24，会被判错！
```

所以引擎内部**完全不用浮点**，而是用既约分数 `{n, d}`（`d > 0`，已约分）：

```js
加法：frac(a.n*b.d + b.n*a.d, a.d*b.d)
减法：frac(a.n*b.d - b.n*a.d, a.d*b.d)
乘法：frac(a.n*b.n,          a.d*b.d)
除法：frac(a.n*b.d,          a.d*b.n)      // b.n === 0 时返回 null
```

判等只需比较整数：`d === 1 && n === 24`。全程零误差。

1~13 范围内一共有 **16 道**"必须用分数才能解"的经典题，它们被全部放进了最后一章。

### 2.4 去重与规范化

`a + b` 和 `b + a` 是同一个解法。做法是在合并时，对**可交换运算**按子表达式的字符串排序，
让等价形式收敛到同一个字符串，最后用 `Set` 去重。

这能消掉交换律冗余，但**消不掉结合律冗余**（`(a+b)+c` 与 `a+(b+c)` 仍是两个字符串）。
所以引擎报告的"解数"是一个**近似计数**——它只用来给关卡排难度，
不参与任何正确性判断。这一点在写文档时必须说清楚，否则容易被误读成"精确解法数"。

### 2.5 提示与答案是两个不同的求解目标

这是本项目最有价值的一个设计决定：

- **答案**：需要给出**完整表达式**。做法是在递归过程中直接携带表达式节点
  （`{值, 表达式串, 顶层优先级}`），合并时顺手拼好带正确括号的字符串。
- **提示**：需要给出**下一步该合并哪两张牌**，而且要**基于玩家当前的盘面**——
  因为玩家可能已经走了一半、甚至走偏了。所以提示是对当前牌面重新求解，返回第一步。

> **踩过的坑**：最初我让"答案"从提示的步骤序列**反推**表达式，结果生成了
> `1+2+7−4` 这种用了手牌里不存在的数字的假表达式。
> 原因是中间结果可能和某张原始牌数值相同，按值反推会产生歧义。
> 改成"递归中直接携带节点"后彻底消失。
> 测试里现在有一条断言专门守这个：还原出的表达式必须等于 24，**且恰好用完四张牌**。

搜索用记忆化加速，但**只缓存"无解"状态**——因为可解性只取决于数值多重集，
与表达式怎么写无关；而"有解"一旦命中就立即返回，本来也不需要缓存。

### 2.6 性能

| 操作 | 耗时 |
|---|---|
| 单次全解枚举（7680 次叶子评估） | 约 1~3 ms |
| 分析 1~13 全部 1820 个组合 | 约 1.5 s（**构建期一次性完成**） |
| 运行时取任意一关 | **0 ms**（关卡已固化成数据） |

### 2.7 生成 vs 固化

300 关如果每次打开都现场搜索，iPad 上要等 2~4 秒。
所以 `tools/gen-levels.cjs` 在**构建期**把 300 关算好，编码成 `'ABCE'` 这样的
4 字符（`A`~`M` 代表 1~13，共 1200 字符、9 KB）内联进 HTML。
运行时零等待，而且**跨设备题目完全一致**。

## 三、300 关的难度建模

### 3.1 先把家底摸清

枚举 1~13 全部 1820 个四数组合，结果是：

- **1362 个可解**（约 75%）
- 解数分布很宽：从 1 个解到最多 69 个解
- **"必须用分数"的只有 16 个**

> **踩过的坑**：我最初按直觉设计了"第 13/14/15 章专门考分数"，
> 每章 20 关，需要 60 道分数题——实际只有 16 道，根本凑不出来。
> 数据一跑出来就发现方案不可行，于是改成"16 道分数题全部集中在最后一章"。

### 3.2 难度分怎么定

最直接的思路是"解越少越难"，但**它是错的**：

| 牌面 | 解数 | 新手感受 |
|---|---|---|
| `1,2,3,4` | 30 | 很容易 |
| `1,4,8,12` | **69** | **很难**（数字大、关系绕） |

所以难度分以**牌面量级**为主导：

```
难度 = (最大牌面 − 1) × 4            // 主导项：数字越大越难
     + (总和 − 4) / 48 × 2           // 次要项
     + (1 − min(解数, 40)/40) × 1.5  // 再次：解越少越难
     + (必须用分数 ? 60 : 0)          // 直接判为最难，独占最后一章
```

### 3.3 从曲线上均匀取样

把全部 1346 个（去掉四张全同的）可解牌面按难度分升序排成一条曲线，
从这条曲线上**均匀取 280 个点**，每 20 个切成一章，得到第 1~14 章；
最后 20 关 = **最难的 4 道普通题 + 全部 16 道分数题**。

这样同时保证了四件事：

1. 300 关**互不重复**
2. 由易到难**严格单调**（章之间、章内关卡之间都是）
3. 第 1 章**全是小数字**（实测最大牌面为 6）
4. 16 道分数经典题**一道都不浪费**

实测曲线（各章最大牌面）：
`6 | 8 | 9 | 9 | 10 | 11 | 11 | 12 | 12 | 12 | 13 | 13 | 13 | 13 | 13`

## 四、儿童模式的数学基础

**只需加减时，四张牌的可达值恰好是全部 16 种 `±a ± b ± c ± d`。**

- 正向：只含加减的表达式树展开后，必然是各项带符号求和。
- 反向：任意一种符号组合都能实现——先把所有正项加起来，再依次减掉负项。

这条结论有两个用处：

1. **出题**：反向构造。枚举 1~maxN 的全部四数多重集，保留"存在某个符号组合等于目标值"的，
   再随机挑一个。这样 100% 保证只用加减就有解，且题目天然多样。
2. **测试**：这本身就是一个与引擎完全独立的判定器，可以在成千上万道题上和引擎交叉验证。

几个实际约束：

- 目标 10 配最大牌面 9：候选充足；配最大 6 更适合小朋友。
- **目标 24 配最大牌面 6 时，唯一可能是 `6 6 6 6`**（四张全同，太单调），
  所以引擎会自动把上限放宽到 9。
- 儿童模式里没有除法，也就不可能出现分数，中间结果最多出现负数——撤销一下就回来了。

## 五、测试策略

三层测试，**核心是"用另一套实现来验证"，而不是自己验自己**。

### 第 1 层：引擎测试（`test/engine.test.cjs`，76 项断言）

| 组 | 内容 |
|---|---|
| 分数算术 | 约分、负分母、除以零、`1/3 + 1/6 = 1/2` |
| 已知题 | `3,3,8,8` 可解 / `1,1,1,1` 无解 / `13,13,13,13` 无解…… |
| **全空间交叉验证** | 1~13 全部 **1820** 个组合，本引擎与独立模板实现结论**完全一致** |
| 分数判定 | `needsFraction` 与独立的整数穷举结果完全一致 |
| 提示求解 | 1362 个可解题目，按提示步骤**模拟走到底**必须真的到 24；还原出的表达式求值必须等于 24 且恰好用完四张牌 |
| 关卡生成 | 300 关全部有解、互不重复、难度单调、第 1 章全小数字、16 道分数题全在末章 |
| 儿童模式 | 8000 道抽样：全部仅用加减可解、牌面在范围内、无四张全同、与独立符号组合判定一致 |

### 第 2 层：真实浏览器端到端（`test/ui_smoke.py`，Playwright + Chromium）

在 **iPad 竖屏 820×1180 / iPad 横屏 1180×820 / 手机 390×844** 三种视口下，
用真实点击跑完整流程：点选交互 → 合并 → 撤销 → 重来 → 提示 → 答案 →
通关结算（校验 3 星与存档）→ 下一关 → 选关页 → 儿童模式连做 4 题 → 切换目标值 →
自由练习 → 设置 → **布局不溢出 / 触控目标 ≥40px / 断网后仍能打开**。

### 第 3 层：构建期复验（`tools/gen-levels.cjs`）

固化关卡时逐关检查：可解、不重复、编码可逆。任何一关不合格就中止构建。

### 测试真正抓到的三个 bug

| # | 症状 | 根因 |
|---|---|---|
| 1 | 引擎测试跑到第 6 节 **600 秒超时** | 关卡生成用拒绝采样，把求解器调用放大了数万倍；改为"全组合枚举 + 缓存"后降到 8.8 秒 |
| 2 | 生成的表达式是 `1+2+7−4`（用了不存在的数字） | 从步骤序列反推表达式有歧义；改为递归中直接携带表达式节点 |
| 3 | 一进儿童模式就白屏 | `newKidPuzzle()` 里把字段写成了 `S.kid.target`，实际是 `S.kidTarget`；**被浏览器测试抓到**（纯 Node 测试测不到 UI） |

## 六、iPad 适配要点

| 问题 | 做法 |
|---|---|
| 刘海 / 圆角遮挡 | `viewport-fit=cover` + `padding: env(safe-area-inset-*)` |
| iOS 地址栏导致高度跳动 | 用 `100dvh` 而不是 `100vh` |
| 双击缩放、双指缩放 | `touch-action: manipulation` + `user-scalable=no` + 拦截 `gesturestart` / `dblclick` |
| 长按选中文字 / 弹出菜单 | `-webkit-user-select: none` + `-webkit-touch-callout: none` |
| 手指点不准 | 所有触摸目标 ≥44px（测试里断言 ≥40px，实测无小目标） |
| 横屏高度不足 | 媒体查询压缩纵向空间、操作按钮改小、首页按钮改为两列 |
| 想要全屏图标 | `apple-mobile-web-app-capable` + `apple-touch-icon`（180px，脚本生成） |
| 离线可玩 | Service Worker 预缓存应用外壳（改动后要 bump 缓存版本号，否则会拿到旧的） |
| 音效要用户手势才能播 | 首次 `touchstart` 时才创建 AudioContext |

## 七、返工记录

第一版做出来之后被否了两次，记在这里当作教训。

### 7.1 "UI 太丑"——因为没有对着原版做

第一版是自己想当然设计的：深绿赌桌渐变背景 + 金色文字 + 带花色的扑克牌。
而原版其实是**纯白底 + 薄荷绿圆角横卡 + 橙色字形**，两者完全不是一个路子。

**教训**：既然是"复刻"，就必须先拿到原版的真实画面，而不是凭对"这类游戏"的印象去设计。
后来用 Playwright 把原版跑起来逐屏截图，才把配色、圆角、按钮的立体边、
卡片的 2×2 排布、运算符无底色这些细节对上。

顺带发现宣传缩略图和游戏实际画面**不一致**（宣传图里爆炸贴是绿色，实际素材是橙色），
所以看截图也要看"实际运行"的那一张。

### 7.2 封面文字重叠

首页副标题用了 `margin-top: -1.2vmin` 去凑视觉间距，直接把副标题压进了主标题里。
**教训**：靠负 margin 调间距是脆的；用正常间距 + `gap` 才不会在某些字号/屏宽下糊在一起。

### 7.3 儿童模式被我擅自改成了算 10

原版和主玩法都是凑 24，我因为"目标小一点更适合小孩"的想当然，
把儿童模式默认目标改成了 10 并加了目标选择器。这是**擅自改需求**。
已改回固定 24——儿童模式和闯关模式目标一致，只是**运算符只有加减**。

> 顺带算了一下：仅用加减凑 24、牌面 1~10 的可用题目共 **56 道**，
> 够随机出题且不会很快重复。

### 7.4 儿童模式不要评分

第一版给儿童模式也加了三星评价和"连对 N 题"。对小朋友来说这是**压力**而不是激励。
现在儿童模式**没有任何分数**：没有星星、没有连对计数、没有用时，
答对之后只有一个**小女孩举手欢呼的小动画**（纯 SVG 画的，不依赖图片和表情字体）。
奖励应该是"开心"，不是"打分"。

### 7.5 操作手感：合并后必须自动选中结果

第一版每次合并完就把选中状态清空了，于是每一步都要**再点一次结果牌**才能继续。
翻原版 `GameScene` 才发现它在合并后调用了 `onCalc1Select(e)`，让结果牌保持选中：

```
原版：牌 → 运算符 → 牌 → 运算符 → 牌 → 运算符 → 牌        （7 次）
改前：牌 → 运算符 → 牌 → 再点结果牌 → 运算符 → …          （10 次）
```

已改成与原版一致。同时把"按真实玩家最短点法走完一关"写成了断言（≤8 次），
防止以后再退化。

写这条测试时还踩了一个坑：结果牌是**左操作数**，但引擎给的解法里它可能是
**右操作数**（例如 `10 − (−5)`），助手一开始直接拿它当左操作数算，
把 `10−(−5)` 算成了 `−5−10`。所以测试助手也必须像真人一样：
遇到不可交换的运算符先切一次首操作数。

## 八、小结

- 24 点的 "AI" 不是学习型 AI，而是**可穷举的确定性搜索**；原版甚至完全没有求解器，
  300 关答案是硬编码字符串。本项目实现了真正的求解器，所以提示能作用于当前盘面、
  答案永远可信、题目可以无限生成。
- 难点不在算法本身，而在**精确算术（分数）、正确去重、以及把"提示"做成对当前盘面有效**。
- 300 关的质量取决于**难度建模**，而"解数"这个直觉指标是错的，必须引入牌面量级。
- 儿童模式的可靠性来自一条干净的数学性质（只加减 ↔ 16 种符号组合），
  它同时给出了出题方法和独立验证方法。
- "复刻"的第一步永远是**先把原版真正跑起来看清楚**，而不是照着印象做。
- 整个项目没有一行外部依赖：引擎、关卡、UI、图标、打包、测试全部自包含。
